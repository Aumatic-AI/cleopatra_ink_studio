01

Multi-Tenant Architecture

There are three common ways to isolate customers from each other. Only one of them is workable once you have more than a handful of studio clients.

ModelHow it worksVerdict
Silo
One database per client		 Each studio gets its own Supabase project. Avoid — every client is a separate ₹2,400+/mo bill and a separate thing to migrate, monitor, and back up. Falls apart past ~5 clients.
Bridge
One database, one schema per client		 Shared project, but each client's tables live in their own Postgres schema. Avoid — a schema migration now has to run N times instead of once. Middle-ground complexity for little real benefit at your scale.
Pool
One database, one schema, tagged rows		 Every table gets an organization_id column. Row-level security makes sure a query for client A can never return client B's rows. Recommended — one codebase, one migration path, one place to monitor. This is what Supabase's RLS is built for, and what most mid-size multi-tenant SaaS products run on.
Why this is safe, not just cheap: isolation doesn't come from separate databases — it comes from every single query being forced through a rule like organization_id = current_organization_id(). Postgres enforces that at the row level, before your application code even runs. A bug in your API can't accidentally leak another studio's data, because the database itself won't return those rows.

03

Permissions & Feature Gating

Your instinct — plan-based defaults, Super Admin overrides, blocked on both ends — is the right shape. Here's the one refinement that keeps it from drifting out of sync with itself.

How "can this client use this feature?" gets decided

An org's effective access to any feature is: the plan's default, unless an override exists for that specific org and feature — in which case the override always wins. One function computes this, and it's the only place that logic lives.

Layer 1 — the screen

On login, the app fetches the org's effective feature set once and hides whatever isn't included — no "AI Design" button shows up for a Base-plan studio. This is convenience, not security.

Layer 2 — the API

Every gated route (/api/generate, /api/generate-rework, …) independently re-checks the exact same effective feature set before doing anything expensive. A disabled feature returns a plain "not included in your plan" error, even if someone calls the API directly.

The rule that keeps both layers honest: one shared function, getEffectiveFeatures(organizationId), used by both the login screen and every gated API route. Never let the frontend and backend maintain two separate copies of "what's allowed" — that's how a hidden button quietly stops matching what the server actually enforces.

Seat limits work the same way

A plan's max_designers / max_admins are checked the moment someone tries to add a new staff member — the "create designer" route counts the org's current active staff and refuses if the limit's already hit, same override logic as any other feature.

05

Logging: What Sentry Actually Is, and What to Use It For

"Logs" covers two genuinely different jobs. Trying to use one tool for both is where this usually goes wrong.

What Sentry is

Sentry watches your app for crashes and unhandled errors — a KEI call that throws, a React component that breaks, an API route that 500s. When one happens, it captures the full stack trace, what the user was doing right before it, and pings you in real time. It's built specifically for "something broke, go look" — not for tracking business events.

JobToolWhy
Crashes & bugs
"the app broke, who needs to know"		 Sentry Purpose-built for this. Free tier covers early scale; genuinely worth paying for once real clients depend on the app.
Business & usage events
"who did what, how much AI has org X used"		 Your own usage_logs table This data has to be joined against your own organizations and plans tables constantly, to enforce quotas and build usage dashboards. A separate log platform makes that join slow and adds a bill for something a plain Postgres table already does for free.

Third-party log platforms (Axiom, Better Stack) exist and are good products, but they're built for raw log-line search across a fleet of servers — not for "how many AI generations has this client used this billing cycle." Skip them; you don't have that problem yet, and your billing logic needs SQL joins, not log search.

Should you compress stored images?

Short answer: yes, but only the copy people view — never the one used to print a stencil.

Keep untouched

The master file — the original image straight from the AI model, exactly as generated. This is the only copy the stencil/print export ever touches. Fine linework and subtle shading are exactly where compression artifacts show up first, and a stencil the artist traces from has zero room for that.

Compress freely

A separate display copy, converted to WebP at high quality (~90) the moment the image is generated or uploaded. Used everywhere the image is only being looked at — chat, dashboard grids, catalog browsing, customer history.

Why this is worth doing: a high-quality WebP typically runs 40–60% smaller than the equivalent PNG, with no visible difference for photographic/design content like this. Storage savings are the smaller win — the real one is egress: every time someone scrolls a chat thread or opens the dashboard, they're re-downloading the display copy, and that traffic is what actually drives your bill at scale (see the earlier egress discussion). Shrinking that file by half shrinks that recurring cost by roughly half too. One conversion step at generation time, two files stored instead of one — small engineering cost for a compounding saving.

Usage limits — the gap in "unlimited"

You've spotted a real gap: right now, nothing stops a customer from hitting "regenerate placement" or "refine again" as many times as they want, in a single session, forever. Every one of those calls the AI model — Placement included, which means even the Base plan has an uncapped AI cost today, despite "no AI generation" being the whole point of that tier.

What's currently unlimitedWhereRecommendation
Placement "generate again" Base Pro — every plan 5 free per session, generous enough nobody notices it; 50 pooled per month as the outer safety net.
Chat refinement rounds Pro only (Base has no chat) Don't cap "rounds" directly — pool every image this plan generates (first batch, refinements, rework, placement — all of it) into one monthly credit count.
WhatsApp marketing sends (new feature — build the limit in before launch, not after) WhatsApp add-on only Separate pool from AI credits — different cost driver. Suggest 500 messages/month included, plus a template-creation cap. See Section 07.
Why one pooled number beats several separate caps: a customer doesn't think in "refinement rounds" vs "placement attempts" — they think "how many times can I generate something." One number (credits_included on the plan, one running counter in usage_logs) is simple to explain, simple to show on a usage bar in the UI, and simple to enforce — the same getEffectiveFeatures()-style check from Section 03 just adds "and do they have credits left."

The point of metering isn't to make the worst case cheaper to run — it's to stop absorbing it silently. A hard cap bounds your cost directly; a pooled quota with billed overage passes the worst case through to the one client actually causing it. Sentry and Resend stay shared platform overhead, not per-client line items, at this scale.
