01

Two Kinds of Permission

RBAC only covers one of these. What you're describing needs both, kept independent.

AxisQuestionGoverned by
Role RBACWhat can this staff member do?admin / designer — unchanged, already exists
Tenant Feature newWhat can this business access, and how much?Plan defaults + per-org overrides
Both must pass. An action succeeds only if the org has the feature AND the staff member's role is allowed to use it. Two independent checks, composed — never merged into one.

03

Access Resolution

One rule, checked the same way for every feature, every time.

  1. Override exists for (org, feature)? → use its enabled flag and limit.
  2. Else → use the plan's default for (plan, feature).
  3. Else → denied. No entry means off, not on.
  4. If enabled with a limit → count this period's usage_logs rows; over the limit is a deny too.

04

Enforcement Pattern

One backend function. One frontend hook. Every feature uses the same two, forever.

Backend — the real gate

getEffectiveAccess(orgId, featureKey) runs first in every gated API route. Denies before any expensive work starts. This is the only place a disabled feature is actually enforced.

Frontend — cosmetic only

useFeature(featureKey) hides nav items and buttons the org can't use. Never trusted for security — the backend check runs independently either way.

Why this is future-proof: a new feature adds a registry key, not new code. Both functions already handle any key you give them.

08

Logging Utility

One shared contract, not one function pretending to run in two places.

  • One file, src/lib/usage-log.ts, exports the full list of valid (feature_key, action) pairs as a typed const — every call site autocompletes from it, typos become type errors
  • It also exports buildLogRow(...) — a pure function that shapes one row: org, staff, session, feature_key, action, target_id, metadata, timestamp
  • Server routes (generation, placement — already service-role, already hold a third-party secret) call logUsageServer(row): inserts via the service-role client, never blocks or fails the parent response, retries once on the known Node→Supabase flakiness
  • Browser-triggered actions (customer, session, staff, trash CRUD) call logUsageBrowser(row): same row shape, inserted via the browser client right alongside the write it's logging
  • The limit check itself — the SELECT count — always runs server-side, in the same route as the gated action, immediately before it. A browser-reported count is never trusted for a security-relevant limit.
Why not one literal universal function: server and browser use different Supabase clients with different trust levels — collapsing them would mean either exposing the service role to the browser, or routing simple CRUD logs through an extra API hop for no reason. One shared row shape and one shared action registry gets the same consistency without that.
Why one table, not a queue or a third-party log service: at this scale (dozens of studio clients, one action per gated request) a single indexed Postgres table is simplest and keeps logs queryable from the Super Admin panel with plain SQL. Revisit only if a single organization's monthly log volume starts running into the hundreds of thousands of rows — the fix then is monthly partitioning of usage_logs, not a new system.

10

Adding a Future Feature

The whole point of this system — this is the entire checklist, every time.

  1. Add one key to the feature registry
  2. Add its default row to plan_features per plan
  3. Wrap the API route: requireFeature(orgId, key)
  4. Wrap the UI: useFeature(key)
No new tables. No new permission logic. No touching Super Admin's code — the new key just appears in its existing UI.
