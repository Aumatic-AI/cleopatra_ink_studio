01

What The App Does Today

An AI-powered tattoo design tool for in-shop staff use. Customers never log in — staff acts on their behalf.

  • Designer looks up or creates a customer by phone, starts a design session
  • AI Design — generate from a style + reference images, refine back-and-forth in a chat thread
  • Rework — cover-up or extend an existing tattoo from a photo
  • Text Tattoo mode — lettering-focused generation; Flash/sticker isolate — clean stencil-ready cutout of a finalized design
  • Upload Existing and Browse Previous Designs — no AI involved
  • Reference tools: Pinterest search, in-browser camera capture, an AI prompt enhancer
  • Placement — describe or photograph the body location, generate a composite preview
  • Finalize (with confirmation), then print an A4 stencil PDF
  • Admin: dashboard (KPIs, 14-day trend, designer leaderboard), designer management, all-customers view, Recently Deleted (30-day soft-delete recovery)

Current Architecture

Full detail lives in this repo's AGENTS.md — read that for anything not covered here. This is the condensed version.

LayerChoice
FrameworkNext.js 16 (App Router), React 19, TypeScript strict
AuthSupabase Auth, cookie-based sessions
Database & StorageSupabase Postgres + Storage — Supabase-only, no S3/R2/AWS
Image generationKEI API (kie.ai) — not Claude or DALL·E
StateZustand, throttled localStorage + Supabase hydration
StylingTailwind v4, dark luxury theme, custom dropdowns only (never native <select>)

Rules the rebuild must keep, not break:

  • Long-running generation is always start-job + poll, never a held-open request — the client polls a status endpoint instead of waiting on one connection
  • Soft-delete only, with a real 30-day retention window before anything hard-deletes — never add an undocumented hard-delete path
  • designer_id means "handled by," not "designer-exclusive" — an admin running a session themself still populates it
  • Short, direct prompts outperform long constraint lists for image-edit fidelity
  • A multi-reference generation batch must rotate which reference leads per slot, or every result anchors on reference #1
  • A role check (admin sidebar, etc.) must re-validate on auth state change, not just on mount

03

Why Rebuild

  • Multiple studio clients are coming — this becomes a multi-tenant, subscription-based SaaS product, not a single-studio tool
  • Feature access and limits (AI generation, seat counts, storage, etc.) must be controlled per client, from a Super Admin panel
  • A disabled feature must be blocked on the backend, not just hidden on the frontend
  • New features (Catalog/folders, WhatsApp Marketing) are wanted but deliberately on hold until this foundation exists

04

Two Kinds of Permission

RBAC only covers one of these. This system needs both, kept independent.

AxisQuestionGoverned by
Role RBACWhat can this staff member do?admin / designer — unchanged, already exists
Tenant Feature newWhat can this business access, and how much?Plan defaults + per-org overrides
Both must pass. An action succeeds only if the org has the feature AND the staff member's role is allowed to use it — two independent checks, composed, never merged into one.

Six tables carry the whole permission system. Every existing tenant-scoped table just gains organization_id.

06

Access Resolution

One rule, checked the same way for every feature, every time.

  1. Override exists for (org, feature)? → use its enabled flag and limit.
  2. Else → use the plan's default for (plan, feature).
  3. Else → denied. No entry means off, not on.
  4. If enabled with a limit → count this period's usage_logs rows; over the limit is a deny too.

07

Enforcement Pattern

One backend function. One frontend hook. Every feature uses the same two, forever.

Backend — the real gate

getEffectiveAccess(orgId, featureKey) runs first in every gated API route. Denies before any expensive work starts. The only place a disabled feature is actually enforced.

Frontend — cosmetic only

useFeature(featureKey) hides nav items and buttons the org can't use. Never trusted for security — the backend check runs independently either way.

Why this is future-proof: a new feature adds a registry key, not new code. Both functions already handle any key you give them.

11

Logging Utility

One shared contract, not one function pretending to run in two places.

  • One file, src/lib/usage-log.ts, exports the full list of valid (feature_key, action) pairs as a typed const — every call site autocompletes from it, typos become type errors
  • Also exports buildLogRow(...) — a pure function shaping one row: org, staff, session, feature_key, action, target_id, metadata, timestamp
  • Server routes call logUsageServer(row) — service-role insert, never blocks or fails the parent response
  • Browser-triggered CRUD calls logUsageBrowser(row) — same row shape, inserted alongside the write it's logging
  • The limit check itself always runs server-side, right before the gated action — a browser-reported count is never trusted for a security-relevant limit
Why one table, not a queue or a third-party service: at this scale, a single indexed Postgres table is simplest and keeps logs queryable from the Super Admin panel with plain SQL.

Feature-Based Folders

Recommended: yes. It pairs directly with the feature registry — the folder name, the registry key, and the permission check all share one name.

src/
  features/                    ← one folder per feature registry key
    ai-design/
      api.ts                   ← handler the route file delegates to
      components/
      prompts.ts
    rework/
    placement/
    customers/
    sessions/
    staff-admin/
    auth/
  app/                         ← routing only — stays thin
    api/
      generate/route.ts        → requireFeature('ai_design') then calls features/ai-design/api.ts
      ...
    (designer)/
    (admin)/
    [sessionId]/
  lib/                         ← truly cross-feature: supabase clients, job store, storage
  components/ui/                ← generic primitives shared by every feature
  • Every route file stays a thin wrapper: check the feature gate, then call into features/<key>/ — the permission key is never more than one line away from the code it gates
  • src/lib/ stays reserved for things genuinely shared across every feature (Supabase clients, the job store, storage helpers) — a lib file that only one feature uses belongs inside that feature's folder instead
  • Do this feature-by-feature, during the "wire existing features into the registry" phase (13, Phase 3) — moving a feature's files is part of the same commit that adds its gate, not a separate big-bang rewrite

13

Migration Plan

Data model and enforcement first. Super Admin UI last — it just manages what already exists by then.

0
Setup

New repo, new Supabase project

Clone the current codebase as-is. Point env vars at the new project. Nothing else changes yet.

1
Foundation

Multi-tenant tables

organizations table, organization_id added everywhere, RLS updated. Backfill one default org so the app keeps working immediately.

2
Foundation

Permission tables + the two functions

plans, plan_features, overrides, usage_logs + getEffectiveAccess() + useFeature(). Everything defaults to enabled — nothing breaks yet.

3
Wire up

Gate existing features, one at a time

AI Design, Rework, Placement, Print — each move gets a registry key, a route wrapper, a UI hook, and its files relocated into src/features/<key>/ (see 12) in the same pass.

4
Built last, on purpose

Super Admin panel

CRUD screens over organizations, plans, and overrides. Fast to build because Phases 1–3 already did the hard part.

5
Deferred — later

New features

Catalog folders, WhatsApp Marketing. On hold until Phases 0–4 are done.

14

Adding a Future Feature

The whole point of this system — this is the entire checklist, every time.

  1. Create src/features/<key>/
  2. Add the key to the feature registry + a default row in plan_features per plan
  3. Wrap the API route: requireFeature(orgId, key)
  4. Wrap the UI: useFeature(key)
No new tables. No new permission logic. No touching Super Admin's code — the new key just appears in its existing UI.
